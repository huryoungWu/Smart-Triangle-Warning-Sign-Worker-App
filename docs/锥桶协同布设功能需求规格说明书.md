## 0. 结论摘要

1. **新增一类业务对象：布设事件（Deployment Event）**。它不是现有“单设备任务”的简单扩展，而是一次多设备协同作业的完整会话，包含 1 个主桶、N 个从桶、参数 L/d、逐级启动链路、异常处置和现场核验记录。
2. **主桶 + 从桶数量**：1 个主桶，1～5 个从桶（N 可配置，默认上限 5）。套装里未被选中的从桶不参与本次事件，也不被占用。
3. **参数口径**：`L` 为主桶目标行程，`d` 为相邻设备的计划启动间隔，两者都是**沿预定布设路线计算的累计行程（米）**，不是地图直线距离，也不是时间。从桶 k 的目标行程为 `L − k·d`。
4. **启动链路是核心**：主桶先启动；主桶自身累计行程达到 `d` 时触发从 1；从 k 自身累计行程达到 `d` 时向主桶上报，主桶收到上报后才触发从 k+1。**绝不能**用“主桶累计走到 2d”触发从 2，也不能把“从 k 已移动 d”当成“从 k 已到达最终位置”。
5. **服务端是协同状态机与占用关系的唯一权威**。APP 负责创建事件、选择设备、下发控制动作、展示状态和现场核验；设备负责自身行程闭环、到间隔上报、启动指令确认与去重。APP 断网或切后台不改变服务端继续编排的事实。
6. **安全底线**：任何异常都必须显性展示；允许暂停、现场处置、按安全流程重试；**不得自动跳过某只桶去启动后续设备**；仅在链路被异常阻断时，允许作业人员经现场安全确认与二次确认后**人工跳过从桶**（主桶不可跳过；全程留痕；事件结果为“带异常完成”）；**不得自动重发运动/启动指令**；上报可以幂等重发，但启动链路不得因重发而重复启动。
7. **完成判定**：设备到达只是“设备报告到达”，必须由现场人员逐只核对实际位置并确认核验通过，事件才算完成。行程反馈不等于精确间距，也不等于现场安全验收。
8. **对现有 APP 的兼容**：保留现有单设备“定距布置/手动遥控”全流程不变；新增“锥桶协同布设”独立入口与独立页面/ViewModel，复用登录、设备二维码扫描、绑定接口、状态刷新、命令票据、记录与上传体系。
9. **接口为草案**：本文第 9 章给出建议的服务端接口与状态 JSON，供后端评审；正式实现前需按第 13 章“待确认问题”逐项定稿。接口改动必须同步更新 APP、`server.js` 与两份后端文档（见 NFR-8）。

## 1. 背景、目标与范围

### 1.1 背景

现有 APP 围绕**单台三角警示牌小车**设计：连接一台设备 → 发布一条路线任务 → 执行 → 核验 → 上传记录。现场若需要沿道路布设多只智能锥桶，现有模型无法表达：

- 多台设备的主/从角色与编队顺序；
- 主桶与从桶之间的逐级启动链路；
- 每台设备独立的累计行程、目标行程、启动/上报结果；
- 设备被其他进行中任务占用时的互斥；
- 多设备事件的整体完成与逐只现场核验。

原始需求已给出业务规则，但未落到本项目现有的三层通信架构、设备台账、状态模型和接口体系。本规格说明书负责把原始需求转化为**可实现、可测试、可验收**的工程需求。

### 1.2 目标

| 编号 | 目标 |
|---|---|
| G-1 | 作业人员可在 APP 内创建一次锥桶协同布设事件，选择主桶与从桶并确定顺序 |
| G-2 | APP 可按 L、d 计算并展示每只桶的目标行程，参数不合法时禁止启动 |
| G-3 | 启动后严格按“主桶 → 从1；从1 → 主桶 → 从2；……”的链路逐级启动，设备可并发移动 |
| G-4 | APP 可实时展示每只桶的编号、角色、顺序、连接、启动、行程、到达、指令与上报结果 |
| G-5 | 异常时 APP 显性告警，支持暂停、现场处置、安全重试、终止；系统不自动跳过、不自动重发运动指令 |
| G-6 | 全部设备到达后，经现场人员逐只核验通过，事件才可完成，并形成可追溯记录 |

### 1.3 本期范围（P0）

- 布设事件创建、设备选择、绑定/解绑、占用校验；
- 参数 L/d 校验与布设预览；
- 协同启动、逐级触发、并发移动；
- 执行页状态展示；
- 暂停 / 继续 / 重试 / 受控人工跳过 / 终止；
- 同一作业人员同一时间只允许一个进行中事件；
- 逐只现场核验与事件完成；
- 本地与服务端事件记录；
- Mock 服务端的多设备与异常场景模拟；
- 与现有单设备流程的兼容与回归。

### 1.4 非目标（本期不做）

- 不实现主桶与从桶之间的直连通信（Q-1 已确认：统一经服务端中继）；
- 不实现地图上的自动路径规划、车道级定位、直线距离换算；
- 不实现自动保持精确间距、自动纠偏、自动补位；
- 不实现异常时**自动**跳过；人工跳过按 FR-6.2 的受控流程执行（仅异常阻断时、仅从桶、需现场安全确认与二次确认、全程留痕），不实现自动重试运动指令；
- 不实现多作业人员同时控制同一事件；
- 不实现设备套装的后台管理界面（套装关系由平台预先维护，仅用于默认候选，不限制从桶加入其他主桶）；
- 不实现 OTA、设备固件升级；
- 不改变现有单设备任务、风险、快照、地图等既有功能。

### 1.5 前置假设

| 编号 | 假设 | 影响 |
|---|---|---|
| A-1 | 锥桶是可移动设备，能按目标行程自主移动，并能上报**自本次启动时刻起**的累计行程 | 若设备只能上报上电累计行程，需服务端保存启动基线并做差值 |
| A-2 | 设备具备角色属性（master/slave）和套装关联；套装由平台预先登记 | APP 只读取，不提供套装编辑；套装仅用于默认候选，任何从桶可加入任意主桶（Q-4 已确认） |
| A-3 | 设备支持启动指令确认（ack）、指令 ID 去重、断链本地停车、急停优先 | 否则无法满足链路可靠性与安全要求 |
| A-4 | 设备能在本地检测“自身累计行程达到 d”的边沿并**恰好上报一次**，不依赖 APP 1Hz 轮询 | d 较小时轮询会严重滞后，必须在设备端边沿触发 |
| A-5 | 所有参演锥桶在启动前按编队顺序置于**同一起始线**，朝向布设方向 | 目标行程公式隐含共同起点；现场核验负责发现偏差 |
| A-6 | `L`、`d` 是沿预定路线的累计行程标量；本期路线为同一条前进通道，不含转向段（Q-11 已确认） | 若需转向路线，需扩展路线模型（P2） |
| A-7 | 服务端可保存事件会话与逐设备事件日志，并在重启后恢复 | 否则 APP 重连/服务端重启后无法继续展示与审计 |
| A-8 | 作业人员已登录；正式环境设备绑定到当前账号或单位 | 演示模式可用 Fake 数据，但不得宣称真实绑定 |

### 2.3 集成前提：现有 APP 的“连接门”

现有主流程为：`登录 → 设备连接（必须连接一台）→ 作业首页 → 发布任务`。

锥桶协同布设是**多设备**流程，不应强制用户先连接某一台单设备。因此本期必须调整入口：

- 登录成功后进入设备连接页；
- 连接页同时提供两个入口：
  1. **单设备作业**：保持现有“选择设备 → 输入绑定码 → 连接 → 作业首页”流程；
  2. **锥桶协同布设**：直接进入布设事件向导，事件内自行完成设备选择与绑定，**不要求先连接单台设备**。
- 作业首页也可增加“锥桶协同布设”入口（若用户已连接单设备），但不得依赖单设备连接状态。

> 该调整是本期 P0 的一部分；否则新功能会被现有连接门阻断。

## 3. 术语、角色与对象

### 3.1 术语

| 术语 | 英文/字段 | 定义 |
|---|---|---|
| 布设事件 | Deployment Event / `deployment` | 一次多锥桶协同布设作业的完整会话 |
| 主桶 | master | 编队首设备，先启动，负责按链路触发从桶 |
| 从桶 k | slave, order=k | 编队中第 k 只从桶，目标行程 `L − k·d` |
| 目标行程 | `targetM` | 设备从本次启动位置到计划位置应行驶的累计行程（米） |
| 当前累计行程 | `traveledM` | 设备自**本次启动时刻**起累计行驶的行程（米），以设备回报为准 |
| 启动间隔 | `d` / `intervalM` | 设备自身累计行程达到该值后，触发下一只桶或向主桶上报；单位米，不是秒 |
| 主桶目标行程 | `L` | 主桶从起始线到计划位置的累计行程（米） |
| 触发 | trigger | 主桶（或经服务端代发）向下一只从桶发送启动指令 |
| 上报 | report | 从桶自身累计行程达到 d 时，向主桶报告“已达到启动间隔” |
| 到达 | arrived | 设备当前累计行程达到其目标行程，由设备报告 |
| 现场核验 | verify | 现场人员逐只核对实际布设位置并确认通过/异常 |
| 绑定 | bind | 把设备登记到账号/单位名下，进入可选设备列表 |
| 加入事件 | join / select | 作业人员在本次事件中选中某台已绑定设备，使其参与本次布设 |
| 占用 | occupied | 设备被某个进行中的事件或任务持有，不能加入其他事件 |
| 起始线 | start line | 所有参演锥桶启动前所在的共同起点线 |

> **绑定 ≠ 加入事件**：绑定只是让设备进入可选列表；只有被本次事件选中，才参与本次布设。APP 文案必须明确区分。

### 3.2 角色

| 角色 | 职责 | 不负责 |
|---|---|---|
| 作业人员 | 创建事件、选设备、设参数、预检、启动、暂停/重试/终止、现场核验 | 不直接计算链路、不绕过服务端 |
| APP | 交互、参数即时校验、状态展示、控制动作发起、本地记录缓存 | 不作为链路权威；不在断网时自行推测设备状态 |
| 服务端 | 设备台账、绑定/占用、事件会话、参数复验、链路编排、超时检测、幂等、审计、记录 | 不替代现场核验 |
| 主桶 | 启动后按自身行程触发从 1；接收从 k 上报后触发从 k+1；自身到达目标 | 不得越级触发、不得按自身行程代替从桶上报 |
| 从桶 | 收到启动指令后按目标行程移动；自身行程达到 d 时上报；到达目标 | 不得直接向下一从桶发送启动指令 |
| 平台/后台 | 预登记套装关系、设备角色、归属 | 本期不提供 APP 内套装管理 |

## 4. 总体方案

### 4.1 架构

沿用现有三层架构：

```text
┌──────────────┐   ① 创建/启动/暂停/重试/核验   ┌──────────────┐   ③ 启动/停止指令   ┌──────────────┐
│ Android APP  │ ─────────────────────────────→ │  服务端       │ ─────────────────→ │  主桶/从桶    │
│              │ ←───────────────────────────── │（会话+链路）  │ ←───────────────── │  （ESP32 等） │
└──────────────┘   ④ 事件聚合状态 1Hz / 记录     └──────────────┘   ② 状态/上报/事件  └──────────────┘
```

- **APP 不直连设备**；APP 只认服务端布设事件接口。
- **服务端是链路权威**：保存事件会话、设备占用、链路步骤、指令/上报日志与超时状态。
- **设备是行程权威**：当前累计行程、是否到达、是否已过 d，均以设备回报为准；APP 不做插值、不做估算。
- **逻辑链路必须满足原始需求**：
  - 主桶 → 从1；
  - 从1 → 主桶 → 从2；
  - 从2 → 主桶 → 从3；
  - 从桶之间不得直接发送下一桶启动指令。

> **物理实现已确认（Q-1）：采用服务端中继**。主桶不与从桶直连；主桶把“自身累计行程达到 d”的触发请求发给服务端，服务端校验后向从 1 下发启动指令；从 k 把“达到 d”的上报发给服务端（报文地址为主桶），服务端校验后由主桶触发从 k+1，或由服务端代主桶下发并在日志中标注 `from=master, relay=true`。逻辑链路、触发来源与审计记录必须符合第 7.3 节的不变量。

### 4.2 职责分工（RACI）

| 事项 | APP | 服务端 | 主桶 | 从桶 |
|---|---|---|---|---|
| 设备选择/绑定 | 发起与展示 | 校验归属、返回可选列表 | — | — |
| 参数 L/d 校验 | 即时校验、阻止下一步 | 启动前复验、拒绝非法值 | — | — |
| 设备占用 | 展示冲突 | 原子占用/释放 | — | — |
| 链路编排 | 只展示 | 记步骤、判超时、转指令 | 触发下一桶 | 上报、移动 |
| 行程/到达 | 展示 | 聚合、检测异常 | 上报自身 | 上报自身 |
| 暂停/终止 | 发起 | 下发停止、冻结链路 | 停止 | 停止 |
| 人工跳过 | 发起、现场确认与二次确认 | 校验、标记 `skipped_manual`、触发下一只 | — | — |
| 现场核验 | 逐只确认 | 记录 | — | — |
| 审计记录 | 本地缓存 | 权威存储 | 设备日志（可选） | 设备日志（可选） |

### 4.3 关键设计决策

| 编号 | 决策 | 说明 | 状态 |
|---|---|---|---|
| D-1 | 服务端作为协同状态机权威 | APP 断网/切后台不影响链路；多设备状态聚合简单；可审计 | 已确认（Q-1） |

### 4.4 端到端流程

1. **入口**：登录 → 设备连接页 →「锥桶协同布设」（无需先连接单设备）。
2. **步骤 1 设备选择**：
   - 选择主桶（已绑定、在线、空闲、非急停、角色为 master）；
   - 选择任意已绑定且可用的从桶（套装从桶默认列出，也可加入其他主桶的从桶），勾选并排序为从 1…从 N；
   - 可扫码/输入编号绑定新设备；可解绑符合条件的设备；
   - 被其他进行中事件/任务占用的设备不可选；执行中的设备不可解绑。
3. **步骤 2 参数与预览**：
   - 输入 L、d；
   - 校验 `d > 0`、`L ≥ N·d`、范围与精度；
   - 展示主桶 L、从 k `L − k·d` 的预览。
4. **步骤 3 预检与开始**：
   - 展示摘要与自动条件（全部在线、空闲、已绑定、非急停、参数合法）；
   - 人工确认“起始线/编队顺序/现场安全”；
   - 点击「开始协同布设」。
5. **服务端创建事件并启动**：
   - 若该作业人员已有非终态事件，拒绝创建并返回现有事件 ID；
   - 复验参数与占用；原子占用设备；
   - 向主桶下发启动指令（目标 L、间隔 d）；
   - 主桶 ack 后进入 RUNNING。
6. **逐级启动**：
   - 主桶自身行程 ≥ d → 触发从 1；
   - 从 1 自身行程 ≥ d → 上报主桶 → 主桶触发从 2；
   - 依此类推；所有已启动设备继续向各自目标移动。
7. **执行页展示**：1Hz 聚合状态；每只桶的编号、角色、顺序、连接、启动、累计/目标行程、到达、指令/上报结果；异常横幅；异常时可暂停/重试/受控人工跳过。
8. **到达**：全部设备报告到达（含目标 0 的无需移动设备）或经人工跳过并完成处置 → 事件进入待核验。
9. **现场核验**：逐只核对实际位置或跳过处置方式，记录通过/异常；全部通过后点击「完成布设」（有人工跳过时结果为“带异常完成”）。
10. **记录**：服务端生成事件记录；APP 本地缓存并在记录页可查。

### 4.5 逻辑时序（已确认：服务端中继）

```text
APP           服务端                主桶               从1              从2
 │  创建/开始   │                    │                 │                │
 │─────────────→│ deploy_start(L,d)  │                 │                │
 │              │───────────────────→│                 │                │
 │              │←──── start_ack ────│                 │                │
 │              │                    │── 自身行程≥d ──→│                │
 │              │←─ trigger_request ─│                 │                │
 │              │──── deploy_start ───────────────────→│                │
 │              │←────────────── start_ack ────────────│                │
 │              │                    │←─ 行程≥d 上报 ──│                │
 │              │←─ interval_reached（地址=主桶）───────│                │
 │              │──── deploy_start（from=主桶）───────────────────────→│
 │              │                    │                 │                │
 │              │   （从1、从2继续各自向目标移动，不停车等待）              │
```

> 关键：服务端给从 2 下发启动指令的**原因**必须是“收到从 1 的上报”，而不是“主桶行程达到 2d”。服务端日志必须记录 `causeReportId`。

### FR-3 参数与布设预览

#### FR-3.1 参数定义

| 参数 | 含义 | 单位 | 输入方式 |
|---|---|---|---|
| `L` | 主桶目标行程（从起始线到主桶计划位置） | 米 | 数值输入，精度 0.1 m |
| `d` | 相邻设备的计划启动间隔（自身行程，不是时间） | 米 | 数值输入或快捷档位，精度 0.1 m |
| `N` | 本次实际使用的从桶数量 | 个 | 由步骤 1 的选择结果决定，只读 |

#### FR-3.2 计算规则

- 主桶目标：`target(master) = L`
- 从桶 k 目标：`target(slave k) = L − k·d`，`k = 1…N`
- 参数必须满足：
  - `d > 0`
  - `L > 0`
  - `L ≥ N·d`
  - `L ≤ L_max`（采用 200 m）
  - `d ≤ d_max`（采用 50 m）
  - `N` 在 `1…N_max`（采用 5）
- 由 `L ≥ N·d` 可推出所有 `target(slave k) ≥ 0`。
- **不得**用地图上两点的直线距离替代 L/d；不得用时间（秒）作为 d 的单位。

#### FR-3.3 参数校验与提示

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-3.3.1 | 输入变化时即时校验并展示错误；不得等点击开始才提示 | P0 |
| FR-3.3.2 | 非法时禁用“下一步/开始”；错误文案必须包含具体数值与规则 | P0 |
| FR-3.3.3 | 至少覆盖：d≤0、L≤0、L<N·d、N 超限、L 超上限、d 超上限、非数字、超过 0.1 m 精度 | P0 |
| FR-3.3.4 | 输入框必须限制为数字/小数，避免负数与科学计数法 | P0 |
| FR-3.3.5 | 参数合法时展示绿色“参数校验通过”与计算后的预览 | P1 |

#### FR-3.4 布设预览

APP 必须展示：

1. **数值预览表**：主桶 `L`；从 1 `L − d`；从 2 `L − 2d`；……；从 N `L − N·d`，并显示算式与结果（保留 1 位小数）。
2. **线性示意图**（非地图）：起始线 0 处，主桶在 L，从 k 在 `L − k·d`，相邻间距为 d；标注“沿预定路线累计行程”。
3. **启动链路示意**：主桶 → 从1；从1 → 主桶 → 从2；……，并注明“从桶之间不直接发送启动指令”。
4. **安全说明**：行程反馈只用于逐级启动与进度展示，不代表精确间距，也不等于现场安全验收。

#### FR-3.5 边界情况

| 情况 | 要求 |
|---|---|
| `L = N·d` | 允许；最后一只从桶目标为 0，按“无需移动”处理（见 7.1.4） |
| 最后一只从桶目标 `>0` 但 `<d` | 允许；该从桶只移动到目标，不需要“达到 d 上报”（它没有下一只） |
| 非最后从桶目标 | 数学上必 ≥ d，必须能上报并触发下一只 |
| 参数精度 | 统一 0.1 m；服务端与 APP 使用同一舍入/校验规则 |
| 预览目标为 0 | 显示“0.0 m · 无需移动”，不得显示负值或除零进度 |

### FR-4 启动与逐级触发（核心）

#### FR-4.1 启动前条件

以下条件全部满足才允许启动：

| 条件 | 判定方 |
|---|---|
| 登录有效、服务端可达 | APP/服务端 |
| 1 个主桶 + 1～N_max 个从桶已选 | APP |
| 所有设备已绑定到当前账号/单位、角色正确 | 服务端 |
| 所有设备在线、可用、无进行中任务、未急停锁定 | 服务端（启动时复验） |
| 参数合法（含 L≥N·d） | APP 即时 + 服务端复验 |
| 现场预检人工确认完成 | APP |
| 作业人员无其他进行中事件（Q-6 已确认：同一时间只允许一个） | 服务端 |
| 所有设备按编队顺序置于同一起始线（人工确认） | APP |

任一条件不满足：禁止启动，显示具体原因；**不得部分启动**。

#### FR-4.2 启动顺序

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-4.2.1 | 点击“开始协同布设”后，服务端必须先向主桶下发启动指令；在主桶确认接收前，不得触发任何从桶 | P0 |
| FR-4.2.2 | 主桶启动指令必须携带：事件 ID、指令 ID、目标行程 L、启动间隔 d、角色、本设备顺序、后继设备信息（如有） | P0 |
| FR-4.2.3 | 主桶确认接收后，事件进入 RUNNING；APP 显示“主桶已启动”，从桶仍为“待启动” | P0 |
| FR-4.2.4 | 主桶自身累计行程达到 d 时，必须触发从 1；触发只发生一次 | P0 |
| FR-4.2.5 | 从 k（k=1…N−1）自身累计行程达到 d 时，必须向主桶上报；主桶收到有效上报后触发从 k+1 | P0 |
| FR-4.2.6 | 最后一只从桶 N 没有后继；其达到 d 时仍可上报（信息性），但不触发任何设备 | P0 |
| FR-4.2.7 | 所有设备在收到启动/触发指令前不得移动；收到并确认后立即按自身目标开始累计行程 | P0 |
| FR-4.2.8 | 已启动设备必须继续向各自目标移动，不得在 d 处停车等待下一只 | P0 |
| FR-4.2.9 | 从桶之间不得直接发送下一桶启动指令；服务端必须拒绝/标记 `from=slave` 的触发请求 | P0 |

#### FR-4.3 核心不变量（必须写入代码与测试）

> **INV-1**：`target(master) = L`，`target(slave k) = L − k·d`。
>
> **INV-2**：触发从 k+1 的唯一原因，是收到从 k 的“已达到启动间隔 d”上报（或经服务端幂等重投的同一上报），**不是**主桶累计行程达到 `(k+1)·d`。
>
> **INV-3**：从 k 的上报条件是“从 k 自身累计行程 ≥ d”，不是“从 k 已到达最终目标”。
>
> **INV-4**：设备到达条件是“自身累计行程 ≥ 自身目标行程”，与是否上报无关。
>
> **INV-5**：设备通过 d 后继续移动；多只桶可同时处于移动状态。
>
> **INV-6**：任何异常都不得**自动**跳过某只桶去启动后续设备；仅允许作业人员在链路被异常阻断时，经现场安全确认与二次确认后**人工跳过从桶**（主桶不可跳过），并全程留痕。
>
> **INV-7**：启动/运动指令不得自动重发；上报可以幂等重发。
>
> **INV-8**：从桶不得直接触发从桶；触发者只能是主桶（或服务端明确代主桶下发，并在日志中标注 `from=master, relay=true`）。
>
> **INV-9**：人工跳过不属于正常链路；被跳过设备状态为 `skipped_manual`，不计为到达；事件完成结果必须为 `completed_with_exception` 并在记录中说明原因与处置方式。

#### FR-4.4 举例（必须按此验收）

设 `L=60 m`、`d=10 m`、`N=3`：

| 设备 | 目标行程 | 触发/上报条件 |
|---|---|---|
| 主桶 | 60 m | 自身到 10 m → 触发从 1 |
| 从 1 | 50 m | 自身到 10 m → 上报主桶 → 主桶触发从 2 |
| 从 2 | 40 m | 自身到 10 m → 上报主桶 → 主桶触发从 3 |
| 从 3 | 30 m | 自身到 10 m → 上报（无后继） |

**反例（必须判为错误）**：

- 主桶到 20 m 时触发从 2（错误：应由从 1 的上报到 10 m 触发）；
- 从 1 到 10 m 时标记“从 1 已到达”（错误：从 1 还要继续到 50 m）；
- 从 1 到 10 m 后停车等待（错误：应继续移动）；
- 从 1 上报丢失后自动启动从 2（错误：应显示异常并阻断）。

#### FR-4.5 指令确认与去重

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-4.5.1 | 每条启动/触发指令必须有唯一 `commandId`；设备必须确认接收（ack） | P0 |
| FR-4.5.2 | 设备必须对 `commandId` 去重：重复收到同一指令时不得重复启动，必须返回当前状态与 `duplicate=true` | P0 |
| FR-4.5.3 | 主桶/服务端必须对上报去重：同一 `reportId` 重复到达不得触发第二次 | P0 |
| FR-4.5.4 | 启动指令超时/结果未知时，APP 必须显示“结果未知”，不得显示“已启动”；服务端应先查询设备状态进行 reconcilation，再决定是否允许人工重试 | P0 |
| FR-4.5.5 | 重试启动指令必须复用同一 `commandId`；设备已执行时返回幂等确认，不得二次移动 | P0 |
| FR-4.5.6 | 每个设备的“启动指令结果”和“上报结果”必须可追溯（时间、结果、原因） | P0 |

#### FR-4.6 并发与链路推进

- 主桶触发从 1 后继续向 L 移动；
- 从 1 启动后继续向 `L−d` 移动；
- 后续设备同理；
- 服务端不得因等待某只桶的到达而暂停已启动设备；
- 服务端不得在未确认上一步的情况下推进下一步。

### FR-5 执行状态展示

执行页必须以**服务端聚合状态**为准，1Hz 轮询（页面可见时），支持手动刷新。

#### FR-5.1 每只桶必须展示的字段

| 原始需求字段 | APP 展示 | 数据来源 |
|---|---|---|
| 编号 | `device_code` + 设备名称 | 服务端 |
| 主/从角色 | “主桶”/“从 k” | 服务端 `role`/`order` |
| 编队顺序 | 主桶为 0；从桶 1…N | 服务端 `order` |
| 连接状态 | 在线/离线/未知 | 服务端 `online` |
| 是否已启动 | 待启动/启动中/已启动/无需移动/失败 | 服务端 `startState` |
| 当前累计行程 | `12.3 m` | 服务端聚合的设备回报 |
| 目标行程 | `50.0 m` | 服务端计算/回显 |
| 是否到达 | 未到达/已到达 | 服务端 `arrived` |
| 是否人工跳过/处置 | 未跳过/人工跳过·处置方式 | `skip` |
| 启动指令结果 | 未发送/已发送/已确认/被拒绝/超时/结果未知 | `startCommand.state` |
| 上报结果 | 不适用/等待/已发送/已确认/丢失/超时 | `report.state`；主桶显示“—”，其触发结果见 `trigger` |

#### FR-5.2 整体状态

必须展示：

- 事件状态：准备中/启动中/执行中/已暂停/待核验/核验异常/已完成/已终止/失败；
- 已完成启动的数量 / 总数；
- 已到达的数量 / 总数；
- 已核验通过的数量 / 总数；
- 当前链路下一步（例如“等待从 1 达到 10 m 后上报”“等待主桶触发从 2”）；
- 最近一次更新时间与“非实时”标注（>3 s 未成功刷新）。

#### FR-5.3 展示规则

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-5.3.1 | 主桶排第一，从桶按 order 升序 | P0 |
| FR-5.3.2 | 不得用 APP 侧计时/插值推算累计行程；只展示服务端返回的设备回报值 | P0 |
| FR-5.3.3 | 不得把“指令已发送”展示为“已启动”；以设备 ack/状态为准 | P0 |
| FR-5.3.4 | 不得把“已移动 d”展示为“已到达” | P0 |
| FR-5.3.5 | 目标为 0 的从桶显示“0.0 m · 无需移动”，进度显示 100% 或特殊标识，不做除零 | P0 |
| FR-5.3.6 | 离线设备必须同时显示最后已知行程/状态与“离线”标识，不得伪装成实时 | P0 |
| FR-5.3.7 | 手机与服务端断开时，必须显示“手机与服务器断开”，与“设备离线”区分 | P0 |
| FR-5.3.8 | 状态颜色不得作为唯一信息载体，必须同时有文字 | P0 |

### FR-6 异常处理与安全干预

#### FR-6.1 异常清单

| 异常 | 判定 | 影响 | APP 必须展示 | 允许动作 |
|---|---|---|---|---|
| 设备启动前离线 | 选中设备在线检查失败 | 不能启动 | 设备高亮“离线” | 移除/等待/刷新/重新绑定 |
| 设备运行中离线 | 服务端超过 `T_OFFLINE` 未收到状态/事件 | 该设备本地断链停车；链路可能阻断 | 红色横幅 + 设备卡片“离线” | 暂停、现场处置、恢复后重试、终止 |
| 启动指令超时 | 发出后 `T_ACK` 内无 ack | 目标设备启动未确认 | “结果未知” | 查询状态、幂等重试、终止 |
| 启动指令被拒绝 | 设备/服务端 `accepted=false` | 链路阻断 | 原样展示 reason | 排除后重试、终止 |
| 上报丢失 | 设备行程已 ≥d，但 `T_REPORT` 内无有效上报 | 下一只不启动，链路阻断 | “上报丢失，后续设备不会自动启动” | 请求重报、刷新状态、现场处置、终止 |
| 上报超时/乱序 | 期望从 k 上报，收到其他/重复 | 链路阻断或忽略重复 | 异常详情 | 检查、重试、终止 |
| 到达超时 | 超过预计时间仍未到达 | 设备可能卡住 | “到达超时” | 暂停、现场处置、终止 |
| 超程 | 行程超过目标 + 容差 | 设备可能越过计划位置 | “超程” | 暂停/停止、现场处置、终止 |
| 设备故障/急停 | 状态 `fault`/`estopLocked` | 链路阻断 | 故障/急停 | 现场处置、恢复/终止 |
| 设备被占用冲突 | 启动时服务端 409 | 不能启动 | 冲突设备清单 | 移除/替换/终止 |
| APP 与服务端断开 | 聚合状态请求失败 | APP 非实时；服务端可能继续 | “手机与服务器断开” | 重连、刷新；紧急情况用设备急停 |
| 链路步骤结果未知 | 指令/上报超时 | 不能推进 | “结果未知” | 按安全流程重试、终止 |
| 链路被异常阻断 | 设备离线/上报丢失/启动失败/到达超时等导致下一步无法正常推进 | 后续设备无法按正常链路启动 | 异常原因 + “可人工跳过当前从桶（受控）” | 人工跳过（仅从桶、需现场确认）、重试、暂停、终止 |

> 人工跳过只允许在链路被异常阻断时、对**从桶**使用；主桶不可跳过。每次跳过必须完成现场安全确认与二次确认，并记录原因、操作人、时间、被跳过设备的处置方式；事件完成结果为“带异常完成”。

#### FR-6.2 干预动作

| 动作 | 语义 | 要求 |
|---|---|---|
| 暂停 | 立即停止所有正在移动的设备，冻结链路，不自动推进 | 必须二次确认；显示“暂停中/已暂停”；对未 ack 的设备显示“停止未确认” |
| 继续 | 现场核查后恢复移动与链路 | 必须二次确认；只对已启动/已暂停设备恢复；不得重新触发已完成的步骤 |
| 重试 | 对当前阻断步骤重发同一指令/请求重报 | 仅允许对“超时/丢失/结果未知”步骤；必须幂等；不得自动执行 |
| 终止 | 停止所有设备，结束事件，释放占用，记录原因 | 必须二次确认；离线设备标注“需现场处置”；不自动视为完成 |
| 人工跳过 | 在异常阻断时跳过当前从桶，启动下一只从桶 | 仅异常阻断时可用；仅从桶；必须确认该设备已停止/移出运动路径、下一只启动路径安全；必须二次确认并填写原因与处置方式；不得自动执行；事件结果为“带异常完成” |
| 现场处置 | 作业人员到设备旁处理（扶正、移开、重启等） | APP 只记录备注；不得假装设备已恢复 |

#### FR-6.3 安全底线（必须）

1. **不得自动跳过**任何一只桶去启动后续设备。人工跳过是受控例外：仅在链路被异常阻断时、仅对从桶、经现场安全确认与二次确认后允许，并必须记录原因与处置方式；主桶不可跳过。
2. **不得自动重发启动/运动指令**；只能人工按安全流程重试。
3. 上报可以自动幂等重发（同一 `reportId`），但不得因此触发两次。
4. 暂停必须停止所有正在移动的设备；暂停后不得再发新的启动指令。
5. 终止后不得再推进链路。
6. 任何“结果未知”不得展示为“成功”。
7. 设备离线时，APP 不得假设其已停止；必须提示现场核实。
8. 行程反馈不得用于宣称“间距精确”或“现场安全验收已完成”。

### FR-7 完成、现场核验与记录

#### FR-7.1 到达判定

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-7.1.1 | 设备到达以其自身累计行程 ≥ 目标行程为准（允许设备固件的停车容差，具体值 Q-8） | P0 |
| FR-7.1.2 | 目标为 0 的从桶：被触发后标记“无需移动/已到达”，行程 0.0 | P0 |
| FR-7.1.3 | 所有设备都报告到达或经人工跳过并完成处置后，事件进入“待核验” | P0 |
| FR-7.1.4 | 任一设备未到达、离线、失败或超程，事件不得进入“待核验”，必须先恢复、人工跳过处置或终止 | P0 |
| FR-7.1.5 | “设备报告到达”不得自动等于“事件完成” | P0 |
| FR-7.1.6 | 人工跳过的设备不记为“到达”；其状态为“人工跳过/待处置”，必须记录处置方式（人工摆放到位/移出路线/不参与本次布设）后才可进入完成判定 | P0 |

#### FR-7.2 逐只现场核验

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-7.2.1 | 待核验页必须逐只展示：编号、角色/顺序、目标行程、实际累计行程、到达时间、异常记录 | P0 |
| FR-7.2.2 | 作业人员必须能对每只桶选择“核验通过”或“核验异常”，并可填写备注 | P0 |
| FR-7.2.3 | 核验通过只代表该只桶现场位置被人工确认；不得自动推断其他桶 | P0 |
| FR-7.2.4 | 全部设备（含无需移动与人工跳过设备）核验通过后，“完成布设”按钮才可用 | P0 |
| FR-7.2.5 | 任一设备核验异常时，事件进入“核验异常”；修正后可重新核验，或终止事件 | P0 |
| FR-7.2.6 | 核验动作必须记录操作人、时间、结果、备注 | P0 |
| FR-7.2.7 | APP 必须提示“请核对实际位置、朝向、间距、灯光与现场安全条件”；不得只核对 App 数字 | P0 |
| FR-7.2.8 | 人工跳过的设备必须核验其处置方式（人工摆放到位/移出路线/不参与本次布设）并记录备注；未处置不得完成 | P0 |

#### FR-7.3 完成

- 完成操作必须由作业人员显式触发；
- 完成后事件进入 `COMPLETED`，释放设备占用；
- **无人工跳过**：事件结果 `result=completed`；
- **有人工跳过**：事件结果 `result=completed_with_exception`，记录被跳过设备、原因、操作人、处置方式；不得伪装为正常完成；
- 完成时生成/固化事件记录（服务端权威）；
- 完成后不得再修改核验结果（如需修正，走异常/审计流程，P1）。

#### FR-7.4 记录

事件记录必须包含：

- 事件标识、名称、作业车道、创建人、创建/开始/完成时间；
- L、d、N；
- 主桶与每只从桶的编号、角色、顺序、目标行程、最终累计行程；
- 每只桶的启动指令结果、上报结果、到达结果、核验结果；
- 链路步骤日志（触发者、被触发者、原因上报 ID、时间、结果）；
- 人工跳过记录（被跳过设备、原因、操作人、时间、处置方式、下一只是否已启动）；
- 异常记录与处置备注；
- 暂停/继续/重试/终止记录；
- 设备在线状态与关键时间戳。

记录必须可在“记录”页查看详情；服务端记录为权威，APP 本地缓存用于离线查看。

## 7. 业务规则与状态机

### 7.1 参数公式与边界

#### 7.1.1 公式

```text
target(master) = L
target(slave k) = L − k × d        (k = 1..N)
```

#### 7.1.2 校验（APP 与服务端必须同一套）

```text
N >= 1
d > 0
L > 0
L >= N × d
L <= L_max
d <= d_max
N <= N_max
```

采用值（Q-3 已确认）：`N_max = 5`、`L_max = 200 m`、`d_max = 50 m`、精度 `0.1 m`。

#### 7.1.3 非最后从桶的上报可行性

当 `L ≥ N·d` 且 `k ≤ N−1` 时：

```text
target(slave k) = L − k·d ≥ (N − k)·d ≥ d
```

因此非最后从桶一定能达到 d 并上报；最后从桶可能 `target < d`，但它没有后继，只需要到达，不需要“达到 d 上报”。

#### 7.1.4 最后从桶目标为 0

当 `L = N·d` 时，`target(slave N) = 0`：

- 该从桶仍参与编队与核验；
- 被前一只从桶的上报触发时，服务端/主桶向其下发 `deploy_start`，携带 `targetM=0, noMove=true`；
- 设备必须 ack 并立即报告 `arrived`（不移动）；
- APP 显示“0.0 m · 无需移动 · 已到达（待核验）”；
- 不计为异常，不得自动跳过其核验。

> 若设备固件不支持 `targetM=0`，服务端可将其标记为 `no_move` 并记录“设备不支持零目标，按计划无需移动”，但仍需现场核验；该降级必须在记录中可见。

#### 7.1.5 最后从桶目标 0 < target < d

- 允许；
- 该从桶收到触发后移动到目标；
- 因为它没有后继，不要求“达到 d 上报”；
- APP 的上报结果显示“不适用（最后一只）”；
- 它仍必须报告到达并接受现场核验。

### 7.2 设备选择规则

```text
可选主桶 = { d ∈ 设备台账 | d.bound = 当前账号/单位
                         ∧ d.role = master
                         ∧ d.online = true
                         ∧ d.available = true
                         ∧ d.occupied = false
                         ∧ d.activeTask = none
                         ∧ d.estopLocked = false }

可选从桶 = { d ∈ 设备台账 | d.bound = 当前账号/单位
                         ∧ d.role = slave
                         ∧ d.online = true
                         ∧ d.available = true
                         ∧ d.occupied = false
                         ∧ d.activeTask = none
                         ∧ d.estopLocked = false }
```

- 任意从桶均可加入任意主桶；`setId/masterCode` 只用于默认候选与推荐顺序，不构成选择限制（Q-4 已确认）。
- 同一设备不得同时出现在主桶与从桶列表。
- 选择阶段不占用设备；启动阶段原子占用。

### 7.3 逐级启动规则（核心）

#### 7.3.1 规则表

| 步骤 | 触发条件 | 动作 | 目标 |
|---|---|---|---|
| S0 | 作业人员确认开始 | 服务端向主桶下发启动 | 主桶按 L 移动 |
| T1 | 主桶自身行程 ≥ d | 主桶触发从 1 | 从 1 按 L−d 移动 |
| R1 | 从 1 自身行程 ≥ d | 从 1 上报主桶 | — |
| T2 | 主桶收到 R1 | 主桶触发从 2 | 从 2 按 L−2d 移动 |
| R2 | 从 2 自身行程 ≥ d | 从 2 上报主桶 | — |
| T3 | 主桶收到 R2 | 主桶触发从 3 | 从 3 按 L−3d 移动 |
| … | … | … | … |
| TN | 主桶收到 R(N−1) | 主桶触发从 N | 从 N 按 L−N·d 移动 |
| RN | 从 N 自身行程 ≥ d（若 target ≥ d） | 上报（信息性） | 无后继 |
| A_k | 设备自身行程 ≥ target(k) | 设备报告到达并停车 | — |
| MS_k | 作业人员人工跳过从 k（仅异常阻断时） | 触发从 k+1（若有） | 从 k 标记 `skipped_manual`；从 k+1 按 L−(k+1)d 移动 |

#### 7.3.2 边沿触发与去重

- 设备必须在本地对 `traveled ≥ d` 做**上升沿**检测；跨过阈值只产生一次 `interval_reached`。
- 即使状态轮询多次看到 `traveled > d`，也不得重复上报/触发。
- 主桶对每个 `(deploymentId, predecessorOrder)` 只处理一次有效上报；重复 `reportId` 直接忽略并 ack。
- 服务端对每个 `(deploymentId, stepSeq)` 只允许一条有效启动指令；重复 `commandId` 返回幂等结果。

#### 7.3.3 人工跳过（受控例外）

人工跳过只用于“链路已被异常阻断、现场无法按正常流程恢复”的情况，不是正常启动路径：

- 仅允许对**从桶**使用；主桶不可跳过（主桶异常只能暂停/终止/现场处置）。
- 仅允许在当前阻断步骤为“从 k 无法上报或无法启动”时，跳过从 k 并触发从 k+1；只能跳过当前阻断步骤对应的从桶，不得预跳过尚未轮到启动的从桶。
- 仅在事件处于 `RUNNING` 时可用；`PAUSED` 状态需先继续（resume）再跳过，不得在暂停中启动下一只。
- 必须由作业人员显式发起，完成以下确认：
  - 已确认从 k 已停止或已移出运动路径；
  - 已确认从 k+1 的启动路径安全；
  - 已了解人工跳过会绕过逐级启动链路，事件将记录为“带异常完成”；
- 必须选择处置方式：`placed_manually`（人工摆放到位）/ `removed_from_route`（移出路线）/ `not_required`（不参与本次布设），并填写原因。
- 服务端必须：
  - 先对从 k 下发停止指令（在线时；离线则记录“需现场处置/停止未确认”）；
  - 将从 k 标记为 `skipped_manual`，不记为到达；
  - 若存在从 k+1，校验其在线/空闲后下发启动指令，日志记录 `cause=manual_skip`、`skipRequestId`、操作人、原因；
  - 若从 k 是最后一只，则只标记跳过，不触发任何设备；
  - 不得自动执行；不得因为跳过而把事件标记为正常完成。
- 若从 k+1 不可用（离线/被占用/任务中），跳过请求必须整体失败，不得只标记从 k 而不启动从 k+1；若从 k 已在现场被移出，作业人员只能先恢复从 k+1 后重试跳过，或终止事件（记录现场处置情况）。
- 被跳过设备仍保持占用，直到事件终态并完成处置核验（见 7.8）。
- 被跳过设备若后续恢复并报告移动/到达，必须标记异常（`skip_after_recovery`），不得改回正常到达；由现场处置决定收尾方式。

#### 7.3.4 服务端中继规则（已确认）

- 主桶本地检测到自身 ≥ d 后，向服务端发送 `trigger_request`（`from=master`, `to=slave1`, `cause=master_interval`）；服务端校验后向从 1 下发 `deploy_start`。
- 从 k 向主桶上报时，报文地址为 `to=master`；服务端转发/记录后，由主桶发出 `trigger_request`（`to=slave k+1`, `causeReportId`）；服务端校验后下发。
- 为降低往返延迟，服务端可以在收到**地址为主桶且校验通过**的上报后，代主桶下发下一条启动指令，但必须：
  - 日志记录 `from=master`、`causeReportId`、`relay=true`；
  - 不得基于主桶自身行程或原始状态推断触发；
  - 不得跳过校验。
- 主桶与从桶之间没有直连链路；`from` 永远不得是 slave 到 slave；所有触发/上报均经服务端。

#### 7.3.5 启动指令载荷（逻辑字段）

| 字段 | 说明 |
|---|---|
| `deploymentId` | 事件 ID |
| `commandId` | 唯一指令 ID |
| `role` | master/slave |
| `order` | 0 主桶；1..N 从桶 |
| `targetM` | 本设备目标行程 |
| `intervalM` | d |
| `reportTo` | 从桶上报对象（主桶编号）；主桶为 null |
| `successor` | 后继设备编号/顺序；最后一只为 null |
| `noMove` | 是否无需移动（target=0） |
| `ts` | 时间戳 |

设备收到后必须：
1. 校验 `deploymentId/order/role` 与自身匹配；
2. 去重 `commandId`；
3. 记录本次启动基线（行程从 0 开始）；
4. ack；
5. 按 target 移动（`noMove=true` 时不移动，直接报告到达）；
6. 本地检测 d 边沿并上报；
7. 到达目标后停车并上报到达。

### 7.4 事件状态机

```text
READY ──start──→ STARTING ──master ack──→ RUNNING
                    │                       │
                    │ 明确拒绝/不可恢复      ├──pause──→ PAUSED ──resume──→ RUNNING
                    ↓                       │
                  FAILED                    ├──all arrived / skipped disposed──→ PENDING_VERIFY
                                            │                       │
                                            │                       ├──all verify pass──→ COMPLETED
                                            │                       └──verify fail──→ VERIFY_FAILED
                                            │                                              │
                                            │                                              ├──re-verify──→ PENDING_VERIFY
                                            │                                              └──abort──→ ABORTED
                                            └──abort──→ ABORTED
```

| 状态 | 允许动作 | 说明 |
|---|---|---|
| `READY` | start, cancel | 已创建未启动；设备未占用（或短时预留，见 Q-2） |
| `STARTING` | pause, abort, retry start | 已占用设备；主桶启动指令在途 |
| `RUNNING` | pause, abort, retry blocked step, manual skip (slave only, anomaly blocked) | 链路推进中 |
| `PAUSED` | resume, abort | 所有设备已停止/停止中；链路冻结 |
| `PENDING_VERIFY` | verify, complete, abort | 所有设备已到达，或人工跳过并完成处置 |
| `VERIFY_FAILED` | re-verify, abort | 有核验异常 |
| `COMPLETED` | — | 终态；`result=completed` 或 `completed_with_exception`；释放占用 |
| `ABORTED` | — | 终态；释放占用 |
| `FAILED` | — | 终态；释放占用；需现场确认 |

> **人工跳过不改变事件顶层状态**：事件仍为 `RUNNING`，被跳过设备为 `skipped_manual`；当所有设备到达或跳过并处置后进入 `PENDING_VERIFY`。完成时若有跳过，`state=completed` 且 `result=completed_with_exception`。
>
> **启动超时/结果未知不是 `FAILED`**：`STARTING` 状态下主桶启动指令超时，事件保持 `STARTING`，在 `anomalies[]` 中增加 `start_timeout`，等待状态核对、人工重试或终止；只有设备/服务端明确拒绝且不可恢复时才进入 `FAILED`。
>
> 异常（设备离线、上报丢失、指令超时等）不改变事件顶层状态，而是以 `anomalies[]` 呈现并阻断链路；这样不会因为一个可恢复异常就把事件判死。

### 7.5 单设备状态机

```text
not_started ──start──→ start_sent ──ack──→ start_acked ──move──→ moving
                                                    │                  │
                                                    │ target=0         ├──traveled≥target──→ arrived
                                                    ↓                  │
                                                 no_move               └──pause/stop──→ stopped ──resume──→ moving
start_sent/start_acked/moving ──明确拒绝/不可恢复错误──→ failed
start_sent/start_acked/moving ──人工跳过（仅异常阻断，服务端标记）──→ skipped_manual
```

- `online` 是独立连接标志，不是 phase；离线时保留最后 phase 并显示“离线”。
- `arrived` 后不再接受运动指令；核验单独记录。
- `no_move` 视为已触发、已到达，但仍需核验。
- `skipped_manual`：人工跳过；**不记为到达**；必须记录处置方式（人工摆放到位/移出路线/不参与）并接受核验；主桶不得进入该状态。
- `failed` 不可自动恢复；需人工处置/终止。
- **启动指令超时属于“结果未知”，不是 `failed`**：设备保持 `start_sent`/`start_acked`，`startCommand.state=timeout`，APP 显示“结果未知”；先核对设备状态，再决定幂等重试或终止。

### 7.6 幂等与去重键

| 对象 | 键 | 行为 |
|---|---|---|
| 创建事件 | `clientRequestId` | 重复创建返回同一事件 |
| 启动/触发/暂停/继续/终止 | `commandId` | 重复请求返回当前结果，不重复执行 |
| 设备启动指令 | `commandId` | 设备去重；重复返回 `duplicate=true` 与当前状态 |
| 人工跳过 | `skipRequestId` / `(deploymentId, deviceCode, skipRevision)` | 重复跳过返回当前处置状态；不得重复触发下一只 |
| 间隔上报 | `reportId = deploymentId:deviceCode:interval:seq` | 自动重发；接收方去重；只触发一次 |
| 到达上报 | `reportId = deploymentId:deviceCode:arrived:1` | 去重 |
| 核验 | `(deploymentId, deviceCode, verifyRevision)` | 同一结果幂等；变更记录审计 |
| 完成 | `deploymentId` | 重复完成返回最终状态 |

### 7.7 超时与异常判定

| 常量 | 采用值（Q-3 已确认，均可配） | 说明 |
|---|---|---|
| `T_ACK` | 3 s | 启动指令等待 ack |
| `T_REPORT` | 3 s | 设备行程已 ≥d 后等待上报 |
| `T_DEVICE_OFFLINE` | 5 s | 服务端超过该时间未收到设备状态/事件 |
| `T_APP_STALE` | 3 s | APP 聚合状态过期，标注“非实时” |
| `T_ARRIVAL` | `target / v_min + 30 s` | 到达监控阈值；`v_min` 服务端可配（建议 0.2 m/s） |
| `T_PAUSE_ACK` | 3 s | 暂停/停止指令 ack |
| `T_SKIP_STOP_ACK` | 3 s | 人工跳过时向被跳过设备下发停止的 ack 等待；超时记录 `skip_stop_unconfirmed` |
| `T_SESSION_IDLE` | 30 min | READY 未启动过期（释放预留，若采用） |

> 所有阈值必须服务端可配置；APP 只展示服务端返回的异常，不自行判定链路超时。

### 7.8 占用生命周期

```text
选择（软校验，不占用）
   ↓ 点击开始
服务端事务性占用（STARTING）
   ↓
RUNNING / PAUSED / PENDING_VERIFY / VERIFY_FAILED（持续占用）
   ↓ 完成/终止/失败
确认设备已停止或已现场处置
   ↓
释放占用
```

- 占用粒度为设备，不是套装；未选中的套装从桶不被占用。
- 单设备任务与布设事件共享同一占用域。
- 人工跳过的设备仍保持占用，直到事件进入终态并完成处置核验；不得因跳过而提前释放。
- 服务端重启后必须恢复占用；不得因重启把仍在运动/状态未知的设备释放给其他事件。
- 释放前若设备离线/停止未确认，必须标记“需现场处置”，不得静默释放（Q-9）。

#### 9.4.4 暂停 / 继续 / 终止

```http
POST /api/v1/deployments/{deploymentId}/pause
{ "commandId": "uuid", "reason": "现场人员穿越" }

POST /api/v1/deployments/{deploymentId}/resume
{ "commandId": "uuid", "confirmed": true, "note": "现场已核查" }

POST /api/v1/deployments/{deploymentId}/abort
{ "commandId": "uuid", "reason": "无法恢复" }
```

- 暂停：停止所有正在移动的设备，冻结链路；返回 `state=paused`。
- 继续：仅恢复已启动/已暂停设备；不得重复触发已完成步骤；若设备状态未知，返回 `409 device_state_unknown`。
- 终止：停止所有设备，结束事件，释放占用（满足 7.8 条件）；返回 `state=aborted`。

```http
  "confirmations": {
    "deviceStoppedOrRemoved": true,
    "nextPathSafe": true,
    "understandException": true
  },
  "note": ""
}
```

响应 `202`：

```json
{
  "deploymentId": "dep-7f3a",
  "state": "running",
  "skippedDevice": "CONE-S-002",
  "skippedPhase": "skipped_manual",
  "nextTriggered": "CONE-S-003",
  "resultHint": "completed_with_exception"
}
```

规则：

- 仅当链路被异常阻断且事件处于 `RUNNING` 时允许；正常执行中调用 → `409 skip_not_allowed`；`PAUSED` 需先继续再跳过。
- 只能跳过当前阻断步骤对应的从桶；预跳过尚未轮到启动的从桶 → `409 skip_not_allowed`。
- 仅允许从桶；主桶 → `409 cannot_skip_master`。
- 必须提供三项确认、`reason` 与 `disposition`；缺失 → `400 skip_confirmation_required` / `400 skip_disposition_required`。
- 服务端先向被跳过设备下发停止（在线时，best-effort）；停止未确认时记录 `stopConfirmed=false`，但人工确认可作为继续依据，必须留痕。
- 被跳过设备标记 `phase=skipped_manual`、`arrived=false`，不计入到达；仍保持占用直到事件终态与处置核验。
- 若存在下一只从桶，服务端校验其在线/空闲后启动，日志记录 `cause=manual_skip`；若下一只不可用，整个跳过请求失败，不标记跳过。
- 若被跳过的是最后一只从桶，`nextTriggered=null`；仍需记录处置方式并核验。
- 重复 `skipRequestId` 返回当前状态，不重复触发下一只。
- 有人工跳过的事件完成时 `result=completed_with_exception`。

#### 9.4.5 重试当前步骤

```http
POST /api/v1/deployments/{deploymentId}/retry
{
  "requestId": "uuid",
  "type": "start_command",
  "deviceCode": "CONE-S-002",
  "stepSeq": 4,
  "originalCommandId": "cmd-trigger-1"
}
```

或：

```json
{
  "requestId": "uuid",
  "type": "report",
  "deviceCode": "CONE-S-001",
  "reportId": "dep-7f3a:CONE-S-001:interval:1"
}
```

- `start_command`：必须复用原设备指令 `originalCommandId`（由服务端保存并返回），设备幂等；重试请求本身用 `requestId` 去重。
- `report`：请求设备重发同一 `reportId`；服务端去重后推进。
- 若当前步骤不处于可重试状态：`409 deployment_state_invalid`。
- 重试不得自动执行；必须由 APP 用户显式触发。

#### 9.4.6 逐只核验

```http
POST /api/v1/deployments/{deploymentId}/verify
{
  "deviceCode": "CONE-S-001",
  "result": "pass",
  "note": "位置/朝向正常",
  "revision": 1
}
```

响应：`200 { "verify": { "state": "pass", "verifiedAt": ... } }`

- 仅 `PENDING_VERIFY` / `VERIFY_FAILED` 可核验。
- 人工跳过的设备核验的是**处置结果**（`placed_manually` / `removed_from_route` / `not_required`），不是“到达”。
- `pass`/`fail` 可修改，但必须记录变更日志（revision）。

#### 9.4.7 完成

```http
POST /api/v1/deployments/{deploymentId}/complete
{ "commandId": "uuid" }
```

- 仅当所有设备 `verify=pass` 时允许；否则 `409 not_all_verified`。
- 幂等；重复完成返回最终状态。
- 无人工跳过：`result=completed`；有人工跳过：`result=completed_with_exception`。
- 完成后释放占用。

#### 9.4.8 取消未启动事件

```http
DELETE /api/v1/deployments/{deploymentId}
```

- 仅 `READY` 可取消；`RUNNING` 等必须走 `abort`。

#### 9.4.9 列表 / 详情（记录页）

```http
GET /api/v1/deployments?from=&to=&state=&page=1&size=20
GET /api/v1/deployments?state=active          # 当前作业人员的非终态事件（入口检查用）
GET /api/v1/deployments/{deploymentId}/record
```

列表返回事件摘要（含 `result`、是否有人工跳过）；详情返回 9.5 全量状态 + 核验/异常/人工跳过/链路日志。

### 9.6 服务端 ↔ 设备事件（草案）

#### 9.6.1 服务端 → 设备：启动

```http
POST /api/v1/device/command
{
  "device_code": "CONE-S-001",
  "type": "deploy_start",
  "deploymentId": "dep-7f3a",
  "commandId": "cmd-trigger-1",
  "role": "slave",
  "order": 1,
  "targetM": 50.0,
  "intervalM": 10.0,
  "reportTo": "CONE-M-001",
  "successor": { "device_code": "CONE-S-002", "order": 2 },
  "noMove": false,
  "cause": "report",
  "ts": 1760083200000
}
```

响应沿用 `{ "accepted": true, "cmdId": "..." }`；重复指令返回 `accepted:true, duplicate:true`。

`cause` 取值：`start`（主桶初始启动）、`master_interval`（主桶自身到 d）、`report`（从 k 上报触发）、`manual_skip`（人工跳过触发）。所有指令均由服务端中继下发；主桶不与从桶直连。

#### 9.6.2 设备 → 服务端：事件

```http
POST /api/v1/device/deployment/event
{
  "deploymentId": "dep-7f3a",
  "device_code": "CONE-S-001",
  "type": "interval_reached",
  "reportId": "dep-7f3a:CONE-S-001:interval:1",
  "traveledM": 10.02,
  "ts": 1760083200000
}
```

`type` 取值：

- `start_ack`：启动确认（可含 `duplicate`）
- `interval_reached`：自身达到 d（地址为主桶）
- `arrived`：自身达到目标
- `stopped`：暂停/终止后已停止
- `anomaly`：设备故障/急停/传感器异常
- `heartbeat`：周期状态（若服务端不主动轮询设备）

#### 9.6.3 主桶触发请求

```http
POST /api/v1/device/deployment/trigger
{
  "deploymentId": "dep-7f3a",
  "from": "CONE-M-001",
  "to": "CONE-S-002",
  "cause": "report",
  "causeReportId": "dep-7f3a:CONE-S-001:interval:1",
  "commandId": "cmd-trigger-2",
  "skipRequestId": null,
  "ts": 1760083200000
}
```

服务端校验：

- `from` 必须是本事件主桶；
- `to` 必须是 `causeReportId` 对应从桶的下一只；
- `causeReportId` 必须有效且未被消费；
- `cause=manual_skip` 时 `causeReportId=null`，且必须携带有效的 `skipRequestId`；`to` 必须是下一只从桶；
- 校验失败 → 拒绝并记录异常；不得下发。

> **已确认（Q-1）采用服务端中继**：主桶不直接向从桶下发指令。人工跳过时，服务端先向被跳过设备下发停止（在线时 best-effort），再向下一只从桶下发 `deploy_start`，并记录 `cause=manual_skip`。若未来引入直连，仍必须向服务端上报触发结果以便审计，且不得改变逻辑链路。

## 10. 非功能需求

### NFR-1 安全（最高优先级）

| 编号 | 要求 |
|---|---|
| NFR-1.1 | 任何异常不得**自动**跳过设备；人工跳过按 FR-6.2/7.3.3 的受控流程执行（仅异常阻断、仅从桶、现场确认、二次确认、留痕、带异常完成）；不得自动重发启动/运动指令 |
| NFR-1.2 | 暂停/终止必须停止所有正在移动的设备；停止指令失败必须显性提示 |
| NFR-1.3 | 启动前必须完成在线、空闲、绑定、急停、占用、参数、预检全部校验 |
| NFR-1.4 | 设备离线时 APP 不得假设其已停止；必须提示现场核实 |
| NFR-1.5 | 事件完成必须经过逐只现场核验（含人工跳过设备的处置核验）；不得以设备报告到达代替 |
| NFR-1.6 | UI 不得宣称“精确间距”“自动安全验收”；必须展示安全说明 |
| NFR-1.7 | 急停优先级最高；布设事件不得绕过设备急停 |
| NFR-1.8 | 服务端不得因 APP 断网而停止链路；设备断链由设备本地安全策略处理 |

### NFR-2 性能与实时性

| 编号 | 要求 |
|---|---|
| NFR-2.1 | 执行页可见时 1Hz 聚合状态刷新；离开/切后台停止轮询 |
| NFR-2.2 | 单次聚合状态响应支持 1 主 + 5 从（6 台）在 2 s 内返回 |
| NFR-2.3 | 启动指令端到端 ack 典型 ≤ 2 s；超时阈值 3 s（可配） |
| NFR-2.4 | 上报→下一只启动的端到端延迟目标 ≤ 1 s（服务端中继）；不得因 1Hz 状态轮询才触发 |
| NFR-2.5 | APP 切换页面/重进执行页后 3 s 内恢复展示 |

### NFR-3 可靠性

| 编号 | 要求 |
|---|---|
| NFR-3.1 | 事件会话、设备占用、链路步骤、核验结果持久化；服务端重启可恢复 |
| NFR-3.2 | 指令/上报幂等；重复请求不产生重复动作 |
| NFR-3.3 | APP 与服务端断线重连后，以聚合状态覆盖本地展示，不推断 |
| NFR-3.4 | 服务端不得在设备仍可能运动时释放占用 |
| NFR-3.5 | 关键异常必须进入事件日志，便于追溯 |

### NFR-4 兼容性

| 编号 | 要求 |
|---|---|
| NFR-4.1 | 现有单设备流程、接口字段、记录上传保持兼容 |

| NFR-4.3 | 现有 Mock 数据与联调脚本不被破坏；新增接口独立 |
| NFR-4.4 | 新页面复用现有主题、组件、扫码权限与服务器地址配置 |

### NFR-5 可观测性

| 编号 | 要求 |
|---|---|
| NFR-5.1 | 服务端日志包含：事件 ID、设备编号、步骤、指令 ID、上报 ID、原因上报 ID、人工跳过 ID、时间、结果 |
| NFR-5.2 | APP 调试日志不得记录绑定码/密码 |
| NFR-5.3 | 事件详情可查看完整链路步骤与异常处置记录 |
| NFR-5.4 | 关键指标可统计：启动成功率、上报丢失率、到达超时率、平均触发延迟 |

### NFR-6 安全与权限

| 编号 | 要求 |
|---|---|
| NFR-6.1 | 所有布设接口使用 Bearer 鉴权 |
| NFR-6.2 | 只有设备归属账号/单位可绑定、选择、启动；跨账号返回 403/409 |

| 暂停语义 | 只说“允许暂停” | 暂停=所有移动设备停止+冻结链路；继续需确认 | 安全落地 |
| 重试 | 只说“按安全流程重试” | 同 commandId/幂等；不自动重试运动指令；上报可幂等重发 | 防重复/安全 |
| 人工跳过 | 说“不能自动跳过” | **已确认提供受控人工跳过**：仅异常阻断、仅从桶、现场确认+二次确认+留痕；事件带异常完成；自动跳过仍禁止 | 满足现场处置需要，同时保留安全审计 |
| 完成 | 现场人员确认后完成 | 逐只核验通过后才可完成 | 更严格、可追溯 |
| 记录 | 未展开 | 新增布设事件记录、链路日志、核验记录 | 追溯与审计 |
| 与现有单设备的关系 | 未提及 | 共享设备占用，流程互不破坏 | 兼容 |
| 路线 | “预定布设路线” | **已确认 v1 单向前进通道**，标量行程；转向段后续扩展 | 先跑通核心链路 |
